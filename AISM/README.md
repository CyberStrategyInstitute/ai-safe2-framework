## Why AISM Exists

AI systems are probabilistic by nature. They hallucinate, drift, and behave unexpectedly under novel conditions. Yet most organizations deploy them with governance designed for static software: write a policy, run an audit, repeat annually.

That approach fails for autonomous agents.

The **AI Sovereignty Maturity Model (AISM)** exists because agentic AI systems require governance that operates at runtime, not just at policy review time. When an agent is autonomously executing tasks, chaining tool calls, and orchestrating other agents, a PDF policy document offers no protection. What you need is deterministic control layered over probabilistic behavior, enforced continuously, and measurable at every stage.

AISM provides exactly that.

### Relationship to AI SAFE² v3.1

AI SAFE² defines the control and evidence requirements. AISM provides the maturity model used to measure how completely and robustly an organization has operationalized those requirements.

Version 3.1 does not replace the five AISM maturity levels. It strengthens the operating model around protocol governance, agent-to-tool enforcement, session-independent state semantics, and the separation between framework requirements and reference implementations.

## What Makes AISM Different

AISM was purpose-built for agentic systems where autonomy, non-human identity, memory, delegation, runtime enforcement, and continuous evidence all matter.

## The AISM Value Proposition

### For Security and Risk Leaders

AISM gives you measurable risk posture across AI systems. It helps answer: what is our blast radius if an agent misbehaves? Which pillar is weakest? Where is human authority missing? Which high-autonomy deployments lack sufficient runtime controls?

### For AI and Engineering Teams

AISM translates governance policy into a concrete technical control stack. Every pillar maps to implementation decisions: input sanitization, agent sandboxing, tool authorization, kill switches, memory boundaries, protocol enforcement, and audit evidence.

### For Compliance and Legal Teams

AISM organizes evidence so controls can be mapped across relevant AI, cybersecurity, privacy, and enterprise governance frameworks without running a separate governance program for each one.

### For Executive Leadership

AISM produces an organizational maturity view on a 1-to-5 scale, showing where control exists, where it is weak, and what should be prioritized next.

## The Five Pillars at a Glance

| Pillar | AI-Native Name | What It Governs |
|---|---|---|
| P1 | **Shield** | Input sanitization, prompt injection prevention, data isolation, agent sandboxing, boundary enforcement |
| P2 | **Ledger** | Audit trails, agent behavior logging, asset registry, model inventory, provenance and evidence |
| P3 | **Circuit Breaker** | Kill switches, fail-safe mechanisms, rate limiting, rollback, recovery, continuity |
| P4 | **Command Center** | Human oversight, anomaly detection, intervention workflows, runtime monitoring |
| P5 | **Learning Engine** | Red teaming, threat intelligence, training, evaluation, continuous adversarial learning |

The Cross-Pillar Governance Layer applies across all five pillars and adds ACT tiers, control-plane governance, protocol profiles, catastrophic-risk thresholds, replication governance, and HEAR authority.

## The Five Maturity Levels

| Level | Name | What It Means |
|---|---|---|
| 1 | **Chaos** | Ad hoc AI experiments. No reliable containment, logging, ownership, or oversight. |
| 2 | **Visibility** | Logging and basic containment exist. Operational awareness is improving but controls are inconsistent. |
| 3 | **Governance** | Policies and required controls are defined, assigned, and auditable. |
| 4 | **Control** | Runtime governors enforce deterministic boundaries. Evidence and risk metrics are continuously available. |
| 5 | **Sovereignty** | Full organizational control over identity, delegation, data, evidence, fail-safe authority, and continuous adversarial adaptation. |

## Scoring in 60 Seconds

Each assessment topic is rated across three dimensions:

- **Coverage:** how completely the required controls are implemented;
- **Robustness:** how strongly and consistently those controls are enforced;
- **Sovereignty Assurance:** how much effective organizational control exists over AI authority, evidence, and fail-safe behavior.

Topic scores roll into pillar scores, then into the overall AISM maturity view. The purpose is not to reward documentation volume. It is to measure whether governance exists in practice and can be evidenced.

For methodology details, see [AISM-Scoring-Matrix-Methodology.md](./AISM-Scoring-Matrix-Methodology.md).

### AISM Decision Card

The `safe2 aism` command operationalizes the documented three-metric, five-pillar
model without turning missing evidence into a pass. It produces canonical JSON
for agents and a compact Decision Card for accountable humans:

```bash
safe2 aism init assessment.json
safe2 evidence nexus ./NEXUS --output nexus-evidence.json
safe2 aism ingest nexus-evidence.json --subject-id nexus-local --subject-name "NEXUS Local" --output assessment.json
safe2 aism score assessment.json --format markdown --output decision-card.md
safe2 aism score assessment.json --format json --output decision.json
safe2 aism compare previous.json current.json
```

`ingest` preserves the provider bundle, suggests candidate cells, and requires human confirmation. It never converts scanner presence or endpoint availability directly into maturity ratings. Unverified evidence is explicitly capped in the supplemental decision-support score.

The raw AISM Sovereignty Score remains the normative maturity score. A separately
labeled evidence-adjusted score discounts weak substantiation for decision
support. It does not create another maturity level or claim conformance.

Probability ranges must name an outcome, time horizon, method, and confidence.
When comparable evidence does not exist, the correct result is `NOT ESTIMABLE`,
not an invented percentage.

See the executable [Decision Card example](../examples/aism-decision-card/).

AISM and AI SAFE² maintain mappings across major AI, cybersecurity, privacy, resilience, and enterprise governance frameworks. Representative mappings include:

- NIST AI RMF;

- ISO/IEC 42001;

- MITRE ATLAS;
- EU AI Act;
- SOC 2;
- NIST SP 800-53;
- FedRAMP and CMMC where applicable;
- GSAR Unbiased AI requirements through the UAS regulatory profile extension.

The crosswalk supports evidence reuse. It does not replace an organization's obligation to determine applicability or certification requirements independently.

## v3.1 Implementation Notes

AISM v3.1 uses the same repository-wide distinctions as the framework:

- **161** is the AI SAFE² core framework control count.
- **MCP-1 through MCP-19** are CP.5.MCP profile controls and do not increase the core count to 180.
- **UAS 1.0** is a regulatory profile extension that composes 27 mapped profile requirements. It does not add to the 161-control core or create CP.11 as a core control.
- **NEXUS** is CSI's reference implementation, not a mandatory dependency for AI SAFE² conformance.
- Governance should bind to verified principals, capability grants, delegation, policy, and explicit state handles rather than protocol-owned session constructs.
